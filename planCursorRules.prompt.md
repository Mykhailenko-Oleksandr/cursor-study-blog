## Plan: Cursor Collaboration Rules for cursor-study-blog

TL;DR: Підготувати чіткий набір правил для Cursor у цьому проєкті. Правила базуються на фактичній структурі `client/` та `server/` і підтримують безпечну, мінімальну та зрозумілу роботу з кодом.

Steps

1. Узгодити правила змісту змін.
   - робити тільки ті зміни, які точно вирішують завдання;
   - не міняти архітектуру (React + Vite + Express + MongoDB) без явної згоди;
   - зберігати існуючу організацію `pages`, `components`, `hooks`, `utils`.
2. Фокусуватися на якості фронтенду.
   - використовувати `client/eslint.config.js` як базу для правил;
   - перевіряти лише JS/JSX файли, що працюють з UI, роутингом, state та HTTP;
   - не впроваджувати великі зміни в стилях чи шаблонах без потреби.
3. Фокусуватися на якості бекенду.
   - не змінювати `server/server.js`, якщо не потрібно виправити безпосередньо middleware/CORS/автентифікацію;
   - рекомендувати додати ESLint або тести для `server/`, щоб відповідати фронтенд стандарту;
   - зберігати безпеку: `helmet`, `rate limit`, `express-mongo-sanitize`, валідація в `validators/`.
4. Дотримуватися процесу співпраці.
   - одна гілка = одна задача;
   - кожен PR має мати короткий опис, що змінюється і чому;
   - перед пушем перевіряти локально: `npm run lint` для клієнта, запускати сервер/клієнт.

Relevant files

- `client/eslint.config.js` — ключ до існуючого фронтенд-стилю.
- `client/App.jsx` — структура роутів, яка показує розділення public/admin.
- `server/server.js` — конфігурація CORS, middleware та безпеки.
- `README.md` — опис архітектури та поточної монорепи.

Verification

1. Перевірити, що правила логічно відповідають структурі файлів і існуючому стеку.
2. Перевірити, що правила узгоджуються з GitHub Flow та best practices.
3. Перевірити, що правила не вимагають додаткових залежностей без потреби.

Decisions

- Залишити поточну технологічну стеку: React + Vite + Express + MongoDB.
- Віддавати перевагу мінімальним змінам і поступовому рефакторингу.
- Не впроваджувати TypeScript або глобальні архітектурні зміни без окремої домовленості.
