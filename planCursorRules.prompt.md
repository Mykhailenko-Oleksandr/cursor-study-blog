## Plan: Cursor Collaboration Rules for cursor-study-blog

TL;DR: Це документ для Cursor і AI-асистента. Він описує конкретні правила, приклади гарного і поганого коду, а також процес співпраці для цього репозиторію. Використовувати як джерело істини для прийняття рішень і рев’ю.

Steps

1. Визначити контекст і обсяг.
   - зміни повинні бути мінімальними і вирішувати конкретну задачу;
   - не змінювати архітектуру (React + Vite + Express + MongoDB) без явної згоди;
   - залишати існуючу організацію `pages`, `components`, `hooks`, `utils`.
2. Писати правила для фронтенду.
   - перевіряти `client/src` за правилами React, UI, роутингу, HTTP і state;
   - використовувати `client/eslint.config.js` як джерело стилю та синтаксису;
   - вказувати, коли код має бути перероблений через дублювання або небезпечний рендер.
3. Писати правила для бекенду.
   - зміни у `server/` повинні поважати безпеку, валідацію і структуру маршрутизаторів;
   - уникати змін в `server/server.js`, якщо вони не потрібні для middleware/CORS/auth;
   - рекомендувати додати ESLint або базові тести для `server/`, якщо це покращує якість.
4. Описати процес.
   - одна гілка = одна задача;
   - PR має бути коротким, зрозумілим і з тестами/перевіркою;
   - для AI важливо мати конкретні приклади і «good / bad» правила.

## Основні правила

- Пиши правила конкретно. Уникай абстрактних фраз на кшталт «роби краще». Пиши «не використовуйте...» або «замість цього зробіть...».
- Будь максимально практичним. Якщо правило стосується компонента, додай короткий приклад.
- Орієнтуйся на фактичну структуру цього проекту, а не на загальні шаблони.

## Фронтенд

### Що робити

- Створювати компоненти з однією відповідальністю.
- Використовувати хуки лише в корені компоненту і не викликати їх умовно.
- Використовувати `DOMPurify` для рендерингу HTML з `marked` або `Quill`.
- Використовувати існуючі утиліти та константи, не дублювати URL або рядки.

### Що не робити

- Не писати довгі компоненти, які роблять і рендеринг, і API-запити, і валідацію одночасно.
- Не використовувати `dangerouslySetInnerHTML` без очищення.
- Не дублювати стилі або логіку в кількох компонентах.
- Не обробляти стани у `render` без явної потреби.

### Приклад хорошого фронтенд-коду

```jsx
function BlogCard({ blog }) {
  return (
    <Card title={blog.title}>
      <p>{blog.summary}</p>
      <Link to={`/blog/${blog.id}`}>Read more</Link>
    </Card>
  );
}
```

- Одна відповідальність: відображення блогу.
- Немає внутрішньої логіки побудови URL або запиту.

### Приклад поганого фронтенд-коду

```jsx
function BlogCard({ blog }) {
  const [comments, setComments] = useState([]);
  useEffect(() => {
    fetch(`/api/blog/${blog.id}/comments`)
      .then((res) => res.json())
      .then(setComments);
  }, [blog.id]);

  return (
    <div>
      <h2>{blog.title}</h2>
      <div dangerouslySetInnerHTML={{ __html: blog.content }} />
      <ul>
        {comments.map((c) => (
          <li key={c.id}>{c.text}</li>
        ))}
      </ul>
    </div>
  );
}
```

- Погано: компонент виконує загрузку даних і рендерить небезпечний HTML.
- Потрібно розділити логіку на презентера та контейнер.

## Бекенд

### Що робити

- Використовувати валідацію для вхідних даних перед обробкою.
- Повернути стандартизовану помилку з `errorHandler`.
- Обробляти асинхронні помилки і не ховати їх у `catch`.
- Використовувати middleware для авторизації та обробки запитів.

### Що не робити

- Не писати маршрути без валідації.
- Не обробляти помилки тільки `console.log` і без відповіді клієнту.
- Не залишати hardcoded URI або секрети у коді.

### Приклад хорошого бекенд-коду

```js
router.post("/api/blog", validateBlog, async (req, res, next) => {
  try {
    const blog = await Blog.create(req.body);
    res.status(201).json({ data: blog });
  } catch (err) {
    next(err);
  }
});
```

- Валідація застосовується до запиту.
- Помилка передається через `next(err)` до загального обробника.

### Приклад поганого бекенд-коду

```js
router.post("/api/blog", async (req, res) => {
  try {
    const blog = await Blog.create(req.body);
    res.json(blog);
  } catch (err) {
    console.error(err);
    res.status(500).send("Server error");
  }
});
```

- Погано: немає валідації, помилка ховається і не використовує централізований обробник.

## Процес

### Хороший process

- Гілка: `feature/add-blog-admin-page`
- PR title: `feat: add admin blog list page`
- PR body: коротко описано що змінено, чому і як протестовано.
- Тестування: `npm run lint` у `client/`, запуск серверу, перевірка UI.

### Поганий process

- Гілка: `fix`
- PR title: `update stuff`
- Опис: немає, або тільки `updated code`.
- Немає інформації про тестування.

### Конкретні правила для PR

- Описувати, яку проблему вирішує зміна.
- Писати лише одну логічну групу змін в одному PR.
- Додавати перелік перевірок: `lint`, `run app`, `перевірити admin login`.

## Recommended best practices

- За GitHub Flow: працювати у окремій гілці, створювати PR для злиття у `main`.
- За code review best practices: робити маленькі зміни і пояснювати їх.
- За linting best practices: використовувати ESLint як першочергову перевірку для JS/JSX.
- За security best practices: не допускати небезпечного HTML, додавати `helmet`, `express-mongo-sanitize`, CORS правила.

## Decisions

- Залишити поточну стеку: React + Vite + Express + MongoDB.
- Надавати перевагу мінімальним, цілеспрямованим змінам.
- Не впроваджувати TypeScript або глобальні архітектурні зміни без окремої домовленості.
